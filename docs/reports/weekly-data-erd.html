주보에 설교·문답·파송자를 연결합니다

weekly는 발행일과 구성만 관리하고 sermon·family·sender를 연결합니다. 성경 구절은 bible로 통일하며, 날짜 기반 주보 출력과 콘텐츠 기반 카드를 구분합니다. 운영 DB 반영 구조이며 웹 배포 상태는 별도입니다.

폴더·코드 템플릿 ↗세 콘텐츠 독립 · 주보 조합업무 6개 · 파송자 관계형운영 DB 반영목업 캡처·매핑 ↗
DOMAIN MODEL · v0.7

주보는 세 콘텐츠를 묶고,
각 콘텐츠는 독립적으로 보관합니다.

weekly → sermon / family / sender. 발행일과 출력 선택은 주보, 실제 내용은 각 도메인의 원본입니다. 같은 내용을 다음 주에 쓸 때는 복사하여 과거 주보를 보존합니다.

01 / WEEKLY

주보

date · sections
sermon_id · family_id · sender_id
각 종류 0~1건 연결

02 / SERMON

설교 정리

date · speaker · title
bible = 성경 본문 구절
content = Tiptap 정리

03 / FAMILY

새가족 문답

한 행 = 여러 순을 담은 묶음
groups JSONB에 사진·문답
순·답변 개별 테이블 없음

04 / SENDER

파송자 묶음 + 사람 행

sender는 버전·생명주기
sender_person은 5개 입력 항목
people JSONB 없이 일반 컬럼

실제 콘텐츠는 세 영역, 선택하는 출력은 다섯 가지입니다. 주보 썸네일과 주보 표지는 weekly.date만 사용합니다. 별도 콘텐츠 테이블이 아니며, 3단계 결과·다운로드에서 선택된 경우 앞 1·2페이지에 놓습니다. 설교 표지는 설교 기본 정보를 쓰는 다른 카드입니다.
RELATIONSHIP

주보 없이도 콘텐츠가 존재합니다

weekly
 ├─ sermon_id ─→ sermon
 ├─ family_id ─→ family
 └─ sender_id ─→ sender → sender_person (사람별 행)

family.groups[].photoId ─→ files ─→ Storage
  • 각 FK는 NULL 허용 + UNIQUE + ON DELETE RESTRICT 제안입니다.
  • 현재 한 원본을 여러 주보에 공유하지 않습니다. 다음 주로 복사할 때 새 ID를 만듭니다.
  • 체크 해제는 출력 제외입니다. 원본을 삭제하거나 연결 해제하지 않습니다.
  • 주보 삭제는 콘텐츠 원본의 연쇄 삭제가 아닙니다.
SOURCE VS OUTPUT

날짜 표지와 설교 표지를 구분합니다

출력 순서원본저장 여부
1. 주보 썸네일weekly.date자동 생성
2. 주보 표지weekly.date자동 생성
3. 설교 정리sermon 기본 정보 + content원본만 저장
4. 새가족 문답family.groups + weekly.date원본만 저장
5. 파송자sender_person원본만 저장

선택한 항목만 순서대로 출력합니다. 설교 표지 업로드 사진은 sermon.thumbnail_id로 저장합니다.

FIELD NAMES

passage → bible

sermon.bible는 ‘사사기 7:1-8’ 같은 성경 구절입니다. 볼드·색상·글자 크기가 있는 정리 문서는 sermon.content입니다.

sermon.date        설교 날짜 (weekly.date와 구분)
sermon.speaker     설교자
sermon.title       설교 제목
sermon.bible 성경 본문 구절
sermon.content    Tiptap JSON

family.groups     여러 순의 사진·순장/순원 문답

현재 폼의 sermon.passage는 앱을 연결할 때 text로 이관합니다. 이번 작업은 문서·화면 매핑 변경입니다.

ATOMIC SAVE

버튼은 하나, 저장도 한 트랜잭션

  1. 주보와 연결 원본들의 조회한 version을 함께 전송합니다.
  2. 서버가 Auth·Zod·파일 접근을 확인합니다.
  3. DB 함수/RPC 한 번으로 버전 확인·원본 변경·연결 갱신을 처리합니다.
  4. 하나라도 충돌하거나 실패하면 전체 롤백하고 입력을 보존합니다.
연속된 supabase.update HTTP 호출은 한 트랜잭션이 아닙니다. 독립 원본 편집도 각 version을 비교해야 합니다. 서버 저장 권한 정책과 RPC 구현은 아직 적용하지 않았습니다.
FEATURE-BASED

도메인별 코드, 공통 계약은 하나

src/features/
 ├─ weekly/  발행일·구성·원본 조합·전체 저장 조율
 ├─ sermon/  설교 스키마·조회·원본·카드 생성
 ├─ family/  문답 스키마·조회·원본·카드 생성
 ├─ sender/  사람별 명단 저장·조회·소프트 삭제
 └─ files/   업로드·연결·참조 검증

기존 Next.js 서버 조회·Server Action + supabase-js + Zod를 사용합니다. DB 타입은 Supabase 생성, JSON 타입은 스키마 추론, UI camelCase / DB snake_case 경계에서 한 번 변환합니다. 오류는 공통 Result<T>의 INVALID_INPUT / UNAUTHORIZED / FORBIDDEN / NOT_FOUND / CONFLICT / INTERNAL_ERROR를 사용합니다. 기존 /home · /weekly · /bulletins URL은 유지합니다.

업무 테이블 6개를 운영 DB에 반영했습니다. 파송자는 묶음과 사람 행을 분리합니다. 공개 화면은 유지하고 서버 원본은 팀원 로그인 후 조회·저장합니다. 웹앱 배포는 별도입니다. 원본만 저장하므로 미래 템플릿 변경 후 과거 출력 외형이 바뀔 수 있습니다.
소프트 삭제: 모든 업무 테이블에 deleted_at을 둡니다. 주보 삭제는 원본과 연결을 보존합니다. 활성 주보 날짜만 부분 UNIQUE이며, 연결 중인 원본 삭제는 DB 함수에서 막습니다. 폴더·설교 삭제 레이어 예시 ↗

검토 근거: 현재 저장소의 화면 컴포넌트·폼 스키마·출력 코드·로컬 저장 코드. 목업 동선은 이전 브라우저 확인과 대조했습니다. DB 실측·SQL 실행·운영 정책 적용은 하지 않았습니다. 이 파일은 외부 라이브러리·폰트·API 호출 없이 열리는 독립 HTML입니다. 관계형 FK와 JSONB는 Supabase 공식 문서를 확인했습니다. 도메인 분리·UNIQUE 연결은 이 프로젝트의 설계 판단입니다.
