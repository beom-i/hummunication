사진은 하나로 관리하고,
편집 방식도 하나로 맞춥니다.

추천은 원본 파일 + 현재 편집값입니다. 사진을 교체하면 새 주보 저장이 성공한 뒤 미사용 이전 파일을 정리합니다.

제안용 HTML입니다. 새가족·설교의 공통 화면과 저장 성공·실패·취소 시점을 비교하는 시연이며, 실제 파일 업로드·압축·DB 저장·삭제는 수행하지 않습니다. 상태는 이 페이지의 메모리에만 남습니다.

다만 삭제 순서는 ‘새 사진 저장 성공 → 이전 사진 정리’입니다.

사진2를 골랐어도 취소하거나 저장에 실패할 수 있습니다. 이때 사진1을 먼저 지우면 기존 주보가 깨집니다.

다른 곳에서 쓰는 사진은 남깁니다.

현재는 정리 단계가 빠져 있습니다.

파일 덮어쓰기·물리 삭제를 막아 원본을 보호했지만, 교체 후 미사용 파일을 회수하는 연결은 아직 없습니다. 이 부분을 추가합니다.

03 / RECOMMENDED MODEL

원본 1개와 편집값을 보관하는 안을 추천합니다.

방식다시 편집할 때판단
원본 + 편집값
추천		원본 전체에서 다시 크롭·회전합니다. 품질은 원본에서 다시 계산해 누적 열화를 막습니다. 미리보기·출력에 같은 값을 적용합니다.사진 파일은 하나. 현재 구조를 유지하며 품질 설정과 설교 썸네일 편집값을 추가합니다.
편집 결과 파일로 교체크롭해 버린 영역이나 잃은 화질을 복구하려면 사진을 다시 올려야 합니다.단순하지만 다시 편집하는 지금의 사용 방식에는 맞지 않습니다.
원본 + 편집본 둘 다 저장복구할 수 있지만 사진 두 개의 연결·정리·동기화를 관리해야 합니다.현재 규모에서는 추가 저장 파일 없이 시작합니다. 서버 출력 캐시가 필요해질 때 검토합니다.

현재 코드와 달라지는 점: 지금은 용량 줄이기를 적용하면 압축본으로 파일 연결을 바꿉니다. 추천안은 원본 파일을 계속 연결하고 quality 설정을 저장해 미리보기·내려받기 때 적용합니다. 압축 처리는 원본 전체에 적용한 뒤 같은 크롭·회전값으로 표시하며 압축본은 영구 저장하지 않습니다.

동일하게 만드는 사용자 흐름

  1. 빈 사진 영역 클릭 → 파일 선택 → 편집 모달
  2. 영역 이동·크기 조절, 좌우 90도 회전, 출력 품질 선택
  3. 적용 → 작성 화면의 사진 갱신
  4. 사진 클릭 또는 편집 버튼 → 같은 모달 다시 열기
  5. 교체 → 새 파일로 모달 열기, 취소하면 이전 사진 유지
  6. 삭제 → 작성 화면에서 비우기, 주보 저장 성공 후 미사용 파일 정리

공통 규칙

  • 사진 아래 편집 / 교체 / 삭제 세 버튼을 같은 순서로 둡니다. 사진 위 작은 아이콘 버튼은 사용하지 않습니다.
  • 빈 상태도 용도별 비율을 유지합니다. 새가족은 119:71, 설교 썸네일은 16:9로 고정합니다.
  • 출력 품질: 원본(null), 권장(0.85), 작게(0.65). 품질 변경도 원본 파일은 보존합니다. 압축할 때 긴 변은 최대 2400px로 맞춥니다.
  • PNG/JPG/WebP·5MiB 이하 제한과 서버 파일 검사·RHF/Zod 오류 표시를 공통으로 유지합니다.
  • 업로드·저장 중 공통 좌측 Spinner, 중복 요청 차단, 실패 시 입력 유지. 적용과 주보 저장은 구분합니다.

04 / IMPLEMENTATION SCOPE · 제안

UI·DB·정리를 함께 맞춥니다.

공통 편집값 형식은 같게 하고, 기존 파일 참조 이름은 유지해 변경 범위를 줄입니다. 새 업무 테이블·편집 이력 테이블은 만들지 않습니다.

위치현재제안 변경
새가족 familyphoto_id + photo_edit현재 형식에 quality 추가. 원본 크기는 원본 기준으로 유지. 크롭 비율은 119:71 검증.
설교 sermonthumbnail_id만 저장thumbnail_edit 추가. 같은 편집값 형식으로 16:9 비율을 검증.
파일 filesid / path / created_at / deleted_at 등기존 테이블 활용. 저장 후 참조가 없어진 파일은 삭제 대기, 유예 후 Storage 실파일 정리. DB의 파일 행은 소프트 삭제 기록으로 유지.
클라이언트새가족·설교에 별도 업로드 UIPhotoField 하나와 공통 편집 모달. 용도별 제목·비율만 전달. 서로 다른 원본 ID 필드는 얇은 연결 코드로 유지.
서버주보 저장 트랜잭션, 파일 소프트 삭제 API서버 검증·DB RPC·생성 타입·조회에도 두 편집값 반영. 파일 참조 교체와 미사용 판정은 같은 DB 트랜잭션에서 처리.
실파일 정리자동 정리 없음 · 등록 파일 직접 삭제 차단서버 정리 작업이 참조를 다시 확인한 뒤 Storage API로 제거. 클라이언트 직접 삭제는 열지 않으며 실패는 다음 정리에서 재시도.
저장할 편집값 예시 보기
{
  "rotation": 90,
  "sourceWidth": 4000,
  "sourceHeight": 3000,
  "crop": { "x": 0.1, "y": 0.1, "width": 0.7933333333, "height": 0.355 },
  "quality": 0.85
}

새가족 119:71 예시입니다. crop은 회전된 원본 기준 0~1 좌표입니다. quality=null은 원본 품질, 기존 편집값에 quality가 없으면 null로 읽습니다. 설교는 해당 16:9 비율을 별도로 검증합니다.

파일 정리의 실패·경합 처리

  • 새 파일 업로드 실패나 주보 저장 실패 시 기존 연결·파일은 그대로 둡니다. 성공한 업로드만 남고 저장이 실패한 파일은 미사용 업로드로 회수합니다.
  • 파일 참조를 바꾸는 동안 동일 파일을 정리하지 못하도록 DB에서 파일 행 잠금·참조 검사를 함께 처리합니다. 삭제 대기 파일은 새 콘텐츠에 연결할 수 없게 합니다.
  • 소프트 삭제 콘텐츠가 보존하는 사진도 검사합니다. 다른 참조가 남아 있으면 삭제하지 않습니다.
  • DB와 Storage 삭제는 하나의 트랜잭션이 아니므로 정리 실패로 주보 저장을 실패시키지 않습니다. 유예 후 재검사·재시도합니다. 오래된 미사용 업로드가 회수된 뒤 다시 저장할 때는 재업로드가 필요합니다.

구현 후 완료 기준

  • 두 용도의 빈 상태·사진 상태·버튼·편집 모달 동일
  • 취소 시 사진·크롭·회전·품질 모두 기존 값 유지
  • 적용·저장·재조회 후 같은 사진과 편집값 복원
  • 미리보기·PNG/JPG·확대에서 같은 영역·회전·품질
  • 교체 저장 실패 시 기존 사진 유지, 성공 후 미사용만 회수
  • 공유 파일과 소프트 삭제 원본 참조는 삭제 차단

현재 구현 근거: 새가족 업로드 · 설교 업로드 · 편집 모달 · 파일 API · 파일 참조 보호·소프트 삭제

Supabase 공식 기준: 실파일 삭제는 storage.from(...).remove(...)로 수행해야 합니다. Storage 메타데이터를 SQL로 지워도 실제 파일은 지워지지 않습니다. Delete Objects · Storage Schema · 확인 2026-11-13

이 파일은 UI·파일 수명 정책 제안서입니다. 기존 앱·운영 DB·Storage 정책은 변경하지 않았습니다. 다른 작업의 photo-upload-prototype.html과 별도 파일로 작성했습니다.
