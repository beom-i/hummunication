# 설교·사진 편집 데이터

이번 화면은 기존 `/weekly?step=2` 안에서 `view=sermon`(기본 정보·표지) → `view=sermon-preview`(정리 내용·본문 카드)로 이동한다. 기본 정보는 표지에 즉시 반영한다. 본문 화면의 앨범형·목록형은 같은 페이지들을 보여 주며 카드 클릭으로 확대한다.

## 설교

원본은 `sermon.document`의 Tiptap JSON 하나다. 날짜·설교자·제목·본문 구절은 기존 필드에 저장한다. 허용 문서는 문단·줄바꿈·텍스트이며, 서식은 bold/italic/underline/strike와 textStyle의 color/fontSize다. 글자 크기는 8~32 논리 px, 색상은 6자리 HEX로 검증한다. 취소선 오른쪽의 색상 원을 누르면 기본 10색과 HEX 입력 팝오버가 열린다. 글자 크기는 별도 선택한다.

```json
{
  "date": "2026-11-08",
  "speaker": "담당 목사님",
  "title": "설교 제목",
  "passage": "본문 구절",
  "document": {
    "type": "doc",
    "content": [{ "type": "paragraph", "content": [{
      "type": "text", "text": "강조한 문장",
      "marks": [{ "type": "bold" }, { "type": "textStyle", "attrs": { "color": "#B92330", "fontSize": "18px" } }]
    }] }]
  }
}
```

Enter는 문단을 나눈다. 빈 문단·줄바꿈도 높이를 차지한다. 사용자는 Enter로 위치를 조절하고, 높이가 넘치면 본문 페이지가 자동 추가된다. 별도의 강제 페이지 구분자나 특수 단축키는 없다. 고정 7장·문장 반복·내용 잘라내기는 사용하지 않는다.

출력은 480×600 논리 캔버스, 본문 폭 403.2px·높이 464px다. 같은 HTML/CSS와 로드된 폰트로 높이를 측정하고 미리보기·확대·1200×1500 PNG/JPG를 만든다. 긴 문단이 나뉘어도 인라인 서식과 모든 글자를 유지한다. HTML은 검증한 문서를 허용 태그로 직렬화하며 텍스트는 이스케이프한다. 사용자 HTML·임의 CSS는 저장·삽입하지 않는다. HTML과 분할 결과는 파생 값이며 별도 편집 원본이 아니다.

기존 로컬 드래프트의 `sermon.content` 문자열은 줄바꿈을 보존한 문단으로 변환한다. 저장 때 JSON을 저장하며 복원 실패 시 원본을 지우지 않는다.

## 사진

사진은 클릭하면 재편집 모달을 연다. 전체 사진을 고정해 보여 주고, 선택 영역을 이동하거나 모서리로 크기를 조절한다. 신규 선택 영역은 실제 카드의 사진 슬롯과 같은 16:9이며 해당 비율의 최대 영역으로 시작한다. 기존 119:71 편집값은 계속 읽고, 재편집할 때 16:9로 맞춘다. 좌우 90도 회전 후에도 같은 방식으로 영역을 고르며 적용하거나 취소한다. 원본 사진은 수정하지 않는다.

```json
{
  "photoEdit": {
    "rotation": 90,
    "sourceWidth": 1200,
    "sourceHeight": 800,
    "crop": { "x": 0.05, "y": 0.2, "width": 0.9, "height": 0.358 }
  }
}
```

`crop`은 회전한 이미지의 바운딩 박스 기준 0~1 좌표다. 원본 크기·회전·영역으로 다시 같은 결과를 만들며 확대 배율을 중복 저장하지 않는다. 업로드 미리보기·순 목록·결과 카드·다운로드에 같은 영역을 사용한다. 교체/삭제 시 이전 크롭 정보도 비운다.

신규 사진은 편집 중 Data URL로 보관하고 서버 저장 시 private Storage에 업로드한 `files.id`로 연결한다. 편집 정보는 `family.photo_edit`와 `sermon.thumbnail_edit`에 저장한다. 서버는 파일 참조와 편집값을 다시 검증한다. 저장·재조회·파일 정리 동작은 [사진 처리 문서](photo-workflow.md)를 따른다.

이번 UI 마무리에는 원격 DB 변경이 없다. 연결된 업로드·저장 API는 문서·사진 스키마로 서버 입력을 다시 검증한다. 운영 적용 이력과 실제 계정 검증 범위는 [백엔드 상태 문서](backend-implementation-status.md)를 참고한다.

## 주보 저장·상세 보기

`저장`은 발행일을 ID로 하여 `hummunication.weekly.saved`에 여러 주보를 저장한다. 홈의 최근 주보는 `/bulletins?date=YYYY-MM-DD`에서 읽기 전용으로 열리고, 수정 시 발행일 `YYMMDD`를 입력하면 `/weekly?bulletin=YYYY-MM-DD&step=2`로 이동한다. 비밀번호 자체는 저장하지 않는다. 편집 중 발행일은 고정하며, 신규 작업이 기존 날짜를 덮어쓰는 것은 막는다. 각 단계의 저장은 화면을 유지하고 마지막 단계의 저장은 상세 보기로 돌아간다.

편집 확인은 같은 탭의 sessionStorage 표시로만 유지하고 편집 화면을 떠나면 지운다. 이는 사용자가 요청한 간단한 UI 잠금이며 서버 권한 검증이 아니다. DB·팀 공유·서버 저장은 아직 연결하지 않았다. 사진까지 브라우저 저장 공간에 넣으므로 용량 초과 시 오류를 표시하고 이전 저장본은 보존한다. 기존 단일 드래프트는 새 작업에서 불러오며 첫 저장 성공 후에만 지운다.

기존 홈의 날짜 카드들은 실제 저장본이 없는 동안 `샘플 자료`로 표시한다. 샘플 내용은 현재 목업 기본값이며, 수정·저장하면 해당 날짜의 실제 로컬 저장본으로 바뀐다.
